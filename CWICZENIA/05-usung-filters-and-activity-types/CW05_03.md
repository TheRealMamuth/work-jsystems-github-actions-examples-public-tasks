
# GitHub Actions CI Workflow — Line-by-Line Explanation / Szczegółowe objaśnienie linia po linii

> **File:** `.github/workflows/ci.yml`

---

## 🇬🇧 English

### 1) Goal & Where This File Lives
- **Purpose:** Provide a Continuous Integration (CI) workflow for a Node.js project using GitHub Actions.
- **Location:** Save this file at `.github/workflows/ci.yml` in your repository. GitHub automatically detects workflows placed there.

### 2) Step-by-Step, Line-by-Line

1. ``name: CI``  
   Sets the workflow’s display name (“CI”) shown in the Actions tab and in run logs.

2. ````yaml
   on:
     push:
       branches: [ main ]
       paths-ignore:
         - '05-usung-filters-and-activity-types/dokumentacja/**'
     pull_request:
       branches: [ main ]
       paths-ignore:
         - '05-usung-filters-and-activity-types/dokumentacja/**'
     workflow_dispatch:
   ````
   **`on:`** Declares the events that trigger the workflow.
   - **`push:`** Runs when commits are pushed to the repository.
     - **`branches: [ main ]`** Only triggers on pushes targeting the `main` branch.
     - **`paths-ignore:`** Skips runs if only files under `05-usung-filters-and-activity-types/dokumentacja/**` changed (e.g., documentation-only updates).
   - **`pull_request:`** Runs when a pull request targets the repository.
     - **`branches: [ main ]`** Only triggers for PRs whose base branch is `main`.
     - **`paths-ignore:`** Skips runs if the PR only changes files under `05-usung-filters-and-activity-types/dokumentacja/**`.
   - **`workflow_dispatch:`** Allows manual runs from the GitHub UI (Actions tab → “Run workflow”).

3. ````yaml
   permissions:
     contents: read
   ````
   Sets default permissions for the `GITHUB_TOKEN` provided to this workflow.  
   - **`contents: read`** grants read-only access to repository contents, following the principle of least privilege. Useful for checking out code without unnecessary write permissions.

4. ````yaml
   jobs:
     build:
       runs-on: ubuntu-latest
       defaults:
         run:
           shell: bash
           working-directory: CWICZENIA/05-usung-filters-and-activity-types/
   ````
   Declares the **`build`** job.
   - **`runs-on: ubuntu-latest`**: The job runs on a hosted Ubuntu runner with the latest supported image.
   - **`defaults.run.shell: bash`**: All `run:` steps use Bash by default.
   - **`defaults.run.working-directory: CWICZENIA/05-usung-filters-and-activity-types/`**: All `run:` steps execute from this subdirectory (avoids repeating `cd` commands). Adjust if your project lives elsewhere.

5. ````yaml
       steps:
         - name: Checkout
           uses: actions/checkout@v7
   ````
   Begins the list of steps in the `build` job.
   - **`- name: Checkout`**: Human-friendly label for the step.
   - **`uses: actions/checkout@v7`**: Official action to fetch your repository code onto the runner so subsequent steps can access files.

6. ````yaml
         - name: Ustal wersję Node (przykład)
           uses: actions/setup-node@v7
           with:
             node-version: '24'
   ````
   Sets the Node.js version for the environment.
   - **`uses: actions/setup-node@v7`**: Official action for installing/configuring Node.js.
   - **`with.node-version: '24'`**: Installs Node 24.x. Pinning a major version ensures consistent tooling across runs.

7. ````yaml
         - name: Instalacja zależności
           run: npm ci --include=dev
   ````
   Installs production and dev dependencies in a clean, reproducible way.
   - **`npm ci`**: Uses the lockfile (e.g., `package-lock.json`) to perform a clean install. Faster and more deterministic than `npm install` in CI.

8. ````yaml
         - name: Testy
           run: npm test -- --ci
   ````
   Runs the project’s test suite.
   - **`npm test`**: Executes the test script from `package.json`.
   - **`-- --ci`**: Forwards the `--ci` flag to the underlying test runner (e.g., Jest) to enforce non-interactive, CI-friendly behavior and consistent output.

### 3) How to Deliver This
1. Create the folders if they do not exist: `.github/workflows/`.
2. Add the file `ci.yml` with the contents described above.
3. Commit and push to `main` or open a PR targeting `main`. The workflow will run on `push`, `pull_request`, and on demand via `workflow_dispatch`.

### 4) Useful Notes & Tips
- **Path filters:** `paths-ignore` saves compute time by skipping CI if only documentation paths change.
- **Permissions:** Keep `contents: read` unless your steps need more (e.g., creating releases). Tight permissions reduce risk.
- **Caching (optional):** You can add `actions/setup-node` cache (`cache: 'npm'`) to speed up `npm ci`.
- **Matrix builds (optional):** Use `strategy.matrix.node-version: [22, 24]` to test multiple Node versions if needed.

## 🇵🇱 Polski

### 1) Cel i lokalizacja pliku
- **Cel:** Udostępnić workflow CI dla projektu Node.js z użyciem GitHub Actions.
- **Lokalizacja:** Zapisz plik w katalogu `.github/workflows/ci.yml`. GitHub automatycznie wykrywa workflowy umieszczone w tym miejscu.

### 2) Krok po kroku, linia po linii

1. ``name: CI``  
   Ustala nazwę workflow („CI”), pokazywaną w zakładce Actions oraz w logach uruchomień.

2. ````yaml
   on:
     push:
       branches: [ main ]
       paths-ignore:
         - '05-usung-filters-and-activity-types/dokumentacja/**'
     pull_request:
       branches: [ main ]
       paths-ignore:
         - '05-usung-filters-and-activity-types/dokumentacja/**'
     workflow_dispatch:
   ````
   **`on:`** Deklaruje zdarzenia wyzwalające workflow.
   - **`push:`** Uruchamia się podczas wpychania commitów do repozytorium.
     - **`branches: [ main ]`** Działa tylko dla pushy na gałąź `main`.
     - **`paths-ignore:`** Pomija uruchomienie, jeśli zmienione zostały wyłącznie pliki w `05-usung-filters-and-activity-types/dokumentacja/**` (np. same materiały dokumentacyjne).
   - **`pull_request:`** Uruchamia się dla pull requestów.
     - **`branches: [ main ]`** Tylko dla PR-ów, których gałąź bazowa to `main`.
     - **`paths-ignore:`** Pomija uruchomienie, jeśli PR zmienia wyłącznie pliki w `05-usung-filters-and-activity-types/dokumentacja/**`.
   - **`workflow_dispatch:`** Pozwala ręcznie uruchamiać workflow z interfejsu GitHub (Actions → „Run workflow”).

3. ````yaml
   permissions:
     contents: read
   ````
   Ustawia domyślne uprawnienia dla `GITHUB_TOKEN` dostępnego w workflow.  
   - **`contents: read`** nadaje tylko odczyt do zawartości repozytorium — zgodnie z zasadą najmniejszych uprawnień. Wystarcza do pobrania kodu bez niepotrzebnych praw zapisu.

4. ````yaml
   jobs:
     build:
       runs-on: ubuntu-latest
       defaults:
         run:
           shell: bash
           working-directory: CWICZENIA/05-usung-filters-and-activity-types/
   ````
   Definiuje zadanie **`build`**.
   - **`runs-on: ubuntu-latest`**: Zadanie wykona się na hostowanym runnerze Ubuntu z najnowszym obrazem.
   - **`defaults.run.shell: bash`**: Domyślną powłoką dla kroków `run:` będzie Bash.
   - **`defaults.run.working-directory: CWICZENIA/05-usung-filters-and-activity-types/`**: Wszystkie kroki `run:` wykonają się w tym podkatalogu (nie trzeba powtarzać `cd`). Dostosuj, jeśli projekt leży gdzie indziej.

5. ````yaml
       steps:
         - name: Checkout
           uses: actions/checkout@v7
   ````
   Rozpoczyna listę kroków w zadaniu `build`.
   - **`- name: Checkout`**: Czytelna etykieta kroku.
   - **`uses: actions/checkout@v7`**: Oficjalna akcja pobierająca kod repozytorium na runnera, aby kolejne kroki miały dostęp do plików.

6. ````yaml
         - name: Ustal wersję Node (przykład)
           uses: actions/setup-node@v7
           with:
             node-version: '24'
   ````
   Ustawia wersję Node.js dla środowiska.
   - **`uses: actions/setup-node@v7`**: Oficjalna akcja do instalacji/konfiguracji Node.js.
   - **`with.node-version: '24'`**: Instaluje Node 24.x. Utrzymanie spójności narzędzi między uruchomieniami.

7. ````yaml
         - name: Instalacja zależności
           run: npm ci --include=dev
   ````
   Instaluje zależności produkcyjne i deweloperskie w sposób czysty i powtarzalny.
   - **`npm ci`**: Wykorzystuje plik blokady (np. `package-lock.json`) do deterministycznej, szybkiej instalacji — lepsze w CI niż `npm install`.

8. ````yaml
         - name: Testy
           run: npm test -- --ci
   ````
   Uruchamia testy projektu.
   - **`npm test`**: Wykonuje skrypt testowy z `package.json`.
   - **`-- --ci`**: Przekazuje flagę `--ci` do test runnera (np. Jest), wymuszając tryb nieinteraktywny i spójne raportowanie w CI.

### 3) Jak to dostarczyć
1. Utwórz foldery, jeśli ich nie ma: `.github/workflows/`.
2. Dodaj plik `ci.yml` z opisanymi powyżej treściami.
3. Zacommituj i wypchnij na `main` albo otwórz PR na `main`. Workflow uruchomi się na `push`, `pull_request` oraz ręcznie przez `workflow_dispatch`.

### 4) Wskazówki
- **Filtry ścieżek:** `paths-ignore` oszczędza zasoby, gdy zmiany dotyczą tylko dokumentacji.
- **Uprawnienia:** Pozostaw `contents: read`, chyba że kroki wymagają więcej (np. tworzenie release’ów). Minimalne uprawnienia = mniejsze ryzyko.
- **Cache (opcjonalnie):** W `actions/setup-node` można włączyć cache (`cache: 'npm'`) w celu przyspieszenia `npm ci`.
- **Macierze (opcjonalnie):** Skonfiguruj `strategy.matrix.node-version: [22, 24]`, aby testować wiele wersji Node.
